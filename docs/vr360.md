# 360 / Spherical Video (`--vr360`)

`--vr360` adds a 360-degree video pipeline to easy-ffmpeg. It replaces a
multi-step desktop workflow (PowerDirector / Insta360 Studio / etc.) with
a single command that handles dewarp, encode, and resolution control.

Like every GPU path in this project, `--vr360` is gated behind `--gpu` —
the initial implementation is NVENC-only.

## When to use it

| You have… | Use |
|---|---|
| Dual-fisheye file from a Samsung Gear 360, Insta360, Ricoh Theta, etc. | `--vr360 full` |
| Already-stitched equirectangular file (e.g. `*_Stitch_*.MP4`) | `--vr360 encode` |
| Single-lens 360 fisheye source | `--vr360 full --vr360-input fisheye` |
| Want a high-bitrate intermediate to re-edit later | `--vr360 stitch` |

## Modes

| Mode | What it does | Output bitrate target (4K) |
|---|---|:---:|
| `full` | Dewarp (`v360=input=dfisheye:output=equirect`) + final NVENC encode in one pass | 50 Mbps |
| `stitch` | Dewarp only, high-bitrate NVENC intermediate for later re-edit | 100 Mbps |
| `encode` | No dewarp (input already equirect), just NVENC re-encode | 50 Mbps |

The bitrate target scales with input width:

| Input width | Bitrate target | Stitch mode |
|---|:---:|:---:|
| ≥ 3840 (4K equirect) | 50 Mbps | 100 Mbps |
| ≥ 2048 (2K equirect) | 25 Mbps | 50 Mbps |
| smaller | 12 Mbps | 24 Mbps |

The 50 Mbps default for 4K matches what PowerDirector's high-quality 360
export emits with `libx264` — picked so the GPU output is visually
indistinguishable from a desktop-app render.

## Quick examples

```sh
# Most common: raw dual-fisheye → equirect MP4
easy-ffmpeg gear360_raw.mp4 mp4 --vr360 full --gpu

# Already-stitched Samsung file, just re-encode at default 4K bitrate
easy-ffmpeg 360_0183_Stitch_XHC.MP4 mp4 --vr360 encode --gpu

# Downscale 4K equirect to 1080p equirect (preserves 2:1 aspect)
easy-ffmpeg stitched4k.mp4 mp4 --vr360 encode --gpu --scale 1080p

# Single-lens 360 fisheye with a 210° FOV
easy-ffmpeg single_lens.mp4 mp4 --vr360 full --gpu \
    --vr360-input fisheye --vr360-fov 210

# Stitch only — useful when you'll re-edit in another tool
easy-ffmpeg raw.mp4 mp4 --vr360 stitch --gpu
```

## Resolution control

Output resolution defaults to the **input resolution** (auto-detected via
ffprobe). Pass `--scale` to downsample; upscaling is intentionally not
supported (the source has the most detail).

The `--scale` flag accepts both project names and the familiar p-notation:

| Name | p-notation | Target height |
|---|---|---:|
| `4k` | `2160p` | 2160 |
| `2k` | `1440p` | 1440 |
| `fullhd` | `1080p` | 1080 |
| `hd` | `720p` | 720 |
| `retro` | `480p` | 480 |

For equirectangular content the width is automatically computed to
preserve the 2:1 aspect ratio (so `--scale 1080p` on a 3840×1920 source
produces 2160×1080).

## Input projection (`--vr360-input`)

| Value | Synonym | When |
|---|---|---|
| `dfisheye` | `dual` (default) | Dual-lens 360 cameras: two side-by-side circular images. Samsung Gear 360, Insta360 ONE/ONE R, Ricoh Theta, GoPro Max, etc. |
| `fisheye` | `single` | Single-lens fisheye source. Less common; older 360 cameras with a single >180° lens. |

The default `dfisheye` matches what the overwhelming majority of consumer
360 cameras produce. Only override when you actually have a single-lens
source.

## Field of view (`--vr360-fov`)

The horizontal and vertical FOV of each fisheye lens, in degrees. Default
is `195`, which matches Samsung Gear 360, Ricoh Theta V/Z1, and Insta360
ONE/ONE R. Both the horizontal and vertical FOV are set to the same value
(the v360 filter's `ih_fov` and `iv_fov` parameters).

Override only when your camera's specs say so:

| Camera | FOV |
|---|---|
| Samsung Gear 360 (2016/2017) | 195° |
| Ricoh Theta V / Z1 | 190° |
| Insta360 ONE / ONE R | 200° |
| Insta360 ONE X / X2 / X3 | 210° |
| GoPro Max | 195° |

## Pipeline internals

The dewarp filter (`v360`) runs on CPU in mainline FFmpeg — there's no
`v360_cuda` equivalent. So:

| Mode | Decode | Filter chain | Encode | Pipeline tier |
|---|---|---|---|---|
| `full` | NVDEC (`-hwaccel cuda`) | CPU memory: `v360`, optional `scale` | NVENC | Mixed CPU/GPU |
| `stitch` | NVDEC | Same as `full` | NVENC (higher bitrate) | Mixed CPU/GPU |
| `encode` | NVDEC | GPU memory: `scale_cuda` (if `--scale`) | NVENC | Pure GPU |

`encode` mode is the fastest because frames never leave VRAM. `full` /
`stitch` modes pay a round-trip through system memory for the dewarp,
but it's still faster than CPU encoding end-to-end because the encode
itself is on the GPU.

The encoder args are fixed:

```
-rc vbr -b:v <auto>M -maxrate <auto×1.2>M -bufsize <auto×2>M
-preset p5 -tune hq -profile:v high
```

The level is **not** set — NVENC auto-selects based on the output
dimensions. This avoids the "Invalid Level" crash that strict level
constraints can trigger at non-standard 360 resolutions.

## Comparison with the desktop workflow

A typical PowerDirector / Insta360 Studio export of a dual-fisheye source:

1. Stitch step (dewarp dual-fisheye → equirectangular)
2. Render step (encode to MP4, often `libx264` at ~50 Mbps for 4K)

`--vr360 full` collapses both into one ffmpeg run with NVENC, so 4K 360
encodes drop from "minutes per minute of footage" to "seconds per minute
of footage" on modern RTX cards. The equirectangular output is
bit-identical in projection geometry — the only differences are the
encoder (NVENC vs libx264) and the rate-control mode.

For users who already have stitched files (e.g. from the Samsung
companion app), `--vr360 encode` skips the v360 filter entirely and just
re-encodes with the same high-quality NVENC config.

## Limitations

- **GPU-only**: requires `--gpu`. CPU-only 360 conversion isn't wired up
  yet (the v360 filter is CPU-only anyway, so the only difference would
  be CPU encoding, which is much slower at these bitrates).
- **No spherical metadata injection**: the output is a flat equirect MP4
  without the spatial-media metadata that YouTube/Facebook use to detect
  360 video automatically. If you upload to YouTube, set the
  "360-degree video" flag in the upload UI, or run
  [Google's metadata injector](https://github.com/google/spatial-media)
  on the output.
- **Mono only**: stereoscopic (top-bottom / side-by-side 3D 360) is not
  yet exposed. The v360 filter supports it via `in_stereo`/`out_stereo`
  but the CLI doesn't pass those through.
- **No HDR**: the encoder is fixed to `h264_nvenc` (high profile, 8-bit).
  HDR equirect through `hevc_nvenc` is a follow-up.

## Troubleshooting

### Output looks warped or doubled

Most likely the `--vr360-input` value is wrong. If your source is
side-by-side dual fisheye (two circles), use `dfisheye` (default). If
it's a single fisheye circle, use `fisheye`. If it's already
equirectangular (rectangular 2:1 image), use `--vr360 encode` so no
dewarp is applied.

### Output bitrate is lower than expected

The bitrate target scales with input width. Encoding a 2K source produces
~25 Mbps by default. Pass a larger source (or pre-scale upstream) if you
want the full 50 Mbps target.

### "v360: No such filter"

Your ffmpeg build doesn't include the v360 filter. It's built-in to
libavfilter since FFmpeg 4.1; the Docker image in this project always
includes it. On a host install, rebuild ffmpeg or use the Docker path.
